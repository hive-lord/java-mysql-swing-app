Traffic Management System

A desktop-based system for managing traffic personnel, registered vehicles, violations and fines. Built with a MySQL backend, layered Java core, and a Swing frontend. The repository is currently a documented skeleton: package structure and interfaces are in place, method bodies are marked TODO for implementation.

Design reference: a small, Flock-like operational tool — officers log in, look up vehicles, record violations, and track repeat offenders from a shared desktop console backed by a central database.

1. Overview

What it does. (a) Authenticates traffic staff and administrators. (b) Maintains a registry of vehicles / cases. (c) Records violations, adjusts dues, searches by number / owner / category, and flags repeat or unpaid cases. (d) Provides an audit trail via timestamps and optimistic-locking version fields.

Who uses it. Admin (manages accounts and roles), Traffic Officer / Manager (issues and updates challans), front-desk operator (lookup and reporting). The current UserRole enum — ADMIN, MANAGER, USER — maps directly to these three.

Scope. Offline-first desktop console for a station or checkpoint. Not a real-time signal-control or ANPR system; no web or mobile client in this phase.

2. Architecture

Strict layered design. Each layer only talks to the one below it:

Swing UI (to be built: MainFrame)
  └─> Service layer  (validation, hashing, business rules)
       └─> DAO layer  (JDBC PreparedStatement, ResultSet mapping)
            └─> MySQL (users, vehicles tables)
Config + Util support all layers (JSON config, connections, hashing, money math).

Data flow for a typical action (e.g. issuing a challan): UI collects input → Service validates and applies rules → DAO executes parameterised SQL → MySQL commits → result mapped back to a model object and shown in the UI.

4. File-by-file reference

All paths relative to src/main/java/com/javaproject/. Every file is currently a skeleton — signatures and TODOs are present, bodies return stubs.

model/ — Entities mapped to tables
model/BaseEntity.java
Abstract base class · parent of all entities

Declares the common audit fields every table shares: id, createdAt, updatedAt, version (for optimistic locking). Also owns equals/hashCode (by id) and toString.

  • Traffic use: gives every officer account and vehicle record a stable id plus a change history.
model/User.java (+ UserRole enum, same file)
Account entity → users table

Fields: username, email, passwordHash, firstName, lastName, phoneNumber, active, role, lastLoginAt. Constructor takes (username, email, passwordHash). Helpers: getFullName(); toString() excludes the hash.

  • Traffic use: officer/admin login accounts; role distinguishes ADMIN / MANAGER (senior officer) / USER (officer-operator).
model/Product.java
Registry entity → products table (read: vehicles / challans)

Fields: name, description, sku (unique), price, quantityInStock, reorderLevel, category, active, discontinuedAt. Constructor takes (name, sku, price). Helpers: isLowStock() (qty ≤ reorder level), isAvailable() (active and qty > 0).

  • Traffic use: sku = registration number, price = fine amount, quantity = pending dues/count, category = vehicle class or violation type.
config/ — Database settings object
config/DatabaseConfig.java
Jackson-mapped POJO holding connection settings

Holds host, port, database, username, password, useSSL, serverTimezone, allowPublicKeyRetrieval, connectionTimeout, maxPoolSize with defaults (localhost:3306, javaproject, root). Methods: buildJdbcUrl() composes the JDBC URL; validate() rejects missing host/database/username or bad port.

util/ — Cross-cutting helpers
util/DatabaseConnection.java
Connection manager (single-connection; HikariCP suggested for production)

Constructor stores config and loads the driver once (Class.forName("com.mysql.cj.jdbc.Driver") guarded by AtomicBoolean). getConnection() opens via DriverManager with autoCommit=false. Also: testConnection(), close(), initializeSchema() (CREATE TABLE IF NOT EXISTS for users + vehicles, plus indexes).

util/ConfigLoader.java (+ ConfigException, same file)
Static JSON config reader/writer via Jackson ObjectMapper

loadDatabaseConfig() checks config/database.json then the classpath; loadDatabaseConfig(path) reads a given path; saveDatabaseConfig(config, path) creates directories and pretty-prints JSON; createDefaultConfig(path) writes defaults. Failures surface as ConfigException.

util/PasswordUtil.java
BCrypt wrapper for officer passwords

hashPassword(plain) / hashPassword(plain, logRounds), verifyPassword(plain, hash), needsRehash(hash), generateSalt(), rehashPassword(plain). Work factor LOG_ROUNDS = 12. Plain passwords never touch the database.

util/PriceUtil.java
Exact money arithmetic for fines

SCALE = 2, HALF_EVEN rounding. Static round/add/subtract/multiply/divide/isPositive — every operation re-rounds so fine totals stay to the paisa/rupee cent.

  • Traffic use: fine calculation, late penalties, payment adjustments.
dao/ — Data access (SQL lives here and nowhere else)
dao/GenericDAO.java
Generic CRUD contract for every entity

save / update / deleteById / findById / findAll / existsById / count. Fully defined interface — no TODOs. This is what makes User and Vehicle DAOs interchangeable in tests.

dao/DAOException.java
Checked exception for the DAO layer

Carries operation (e.g. “save”) and entityName (e.g. “User”), with constructors for message / cause, an enriched getMessage(), and a factory mapping SQL codes (duplicate key, foreign key) to readable errors.

dao/UserDAO.java
Officer-account queries (interface, fully defined)

Beyond CRUD: findByUsername, findByEmail, existsByUsername, existsByEmail, findByRole, findActiveUsers, updateLastLogin, searchByName, changePassword.

dao/UserDAOImpl.java
JDBC implementation of UserDAO (all methods stubbed)

Per-method TODOs spell out the exact SQL (e.g. INSERT INTO users … RETURN_GENERATED_KEYS, UPDATE … WHERE id=? AND version=?, case-insensitive LOWER(username)=LOWER(?)), parameter binding, generated-key retrieval, and a private mapResultSetToUser() helper.

dao/ProductDAO.java
Vehicle/challan queries (interface, fully defined — read “Product” as “Vehicle”)

findBySku, existsBySku, findByCategory, findActiveProducts, findLowStockProducts, searchByName, findByPriceRange, updateStock, getStockQuantity, discontinueProduct.

dao/ProductDAOImpl.java
JDBC implementation of ProductDAO (all methods stubbed)

Same pattern as UserDAOImpl plus traffic-relevant guards: negative-dues check in updateStock, version-checked updates, soft-discontinue (active=false, discontinued_at=?), and a mapResultSetToProduct() helper.

service/ — Business rules (validation lives here, not in the UI)
service/ServiceException.java
Checked exception for the service layer

Wraps DAOException with a service-level message (and optional errorCode for future API mapping).

service/UserService.java
Account business operations (interface, fully defined)

registerUser, authenticate, updateProfile, changePassword, findById, findByUsername, getActiveUsers, getUsersByRole, searchUsers, deactivateUser, activateUser, changeUserRole.

service/UserServiceImpl.java
Implementation (stubbed) — regex validation + hashing + uniqueness

Validates username (^[a-zA-Z0-9_]{3,20}$), email pattern, min password length 8; checks existsByUsername/Email; hashes via PasswordUtil; sets role USER and active=true on registration; authenticate tries username then email, verifies hash, stamps last login.

service/ProductService.java
Vehicle/challan business operations (interface, fully defined)

createProduct, updateProduct, adjustStock, findById, findBySku, getActiveProducts, getProductsByCategory, getLowStockProducts, searchProducts, getProductsByPriceRange, discontinueProduct, reactivateProduct, getStockQuantity, getAllCategories.

service/ProductServiceImpl.java
Implementation (stubbed) — validates registration no., fine, counts

Rejects blank name/sku/category, non-positive price, negative quantities; checks existsBySku before create; rounds money via PriceUtil; delegates stock moves to the DAO and surfaces “insufficient dues” as ServiceException.

6. Core workflows

Officer login

Login form → UserService.authenticate → UserDAO.findByUsername / findByEmail → PasswordUtil.verifyPassword → updateLastLogin. Failed logins return empty, never reveal which field was wrong.

Issue / settle challan

Create record → ProductService.createProduct (validate reg. no., round fine) → ProductDAO.save. New offence → adjustStock(+); payment → adjustStock(−) with negative-balance guard. Watchlist → getLowStockProducts; settled → discontinueProduct (soft-close).
