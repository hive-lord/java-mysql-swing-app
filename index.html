Big Brother

An automated system that finds unsafe drivers and flags them — reviewers don't look drivers up, the system surfaces flags on its own. It scores driving-event data (harsh braking, speeding events, violations) and raises a flag when a driver crosses a risk threshold.

1. Overview

What it is. An event-driven flagging pipeline with a reviewer console: (a) driving events are ingested per anonymized driver ID, (b) the service layer validates and scores them, (c) the DAO layer persists counts and scores in MySQL, (d) the Swing console shows only the resulting flag queue for review and resolution.

What it is not.

  • Not officer or citizen surveillance — it watches driving behaviour events, not people.
  • Not a location tracker — no table stores GPS, routes, addresses, or live positions. There is nowhere in the schema to put a location.
  • Not a manual lookup tool — there is no browse-the-database workflow. Existing find/search DAO methods exist in the skeleton but in this deployment they serve the automatic pipeline (fetch one record to score it), not a human search screen. The reviewer UI is flag-queue only.

2. How automatic flagging works

  • Down arrows = calls (service → DAO → MySQL). Each step validates, then persists version-checked.
  • Dashed lines = support/reads (config supplies connections; console polls the flag queue).
  • Flag rule = event count ≥ threshold OR risk score ≥ 7.00 → row appears in getLowStockProducts().

Example: driver DRV-1042 accumulates 3 harsh-braking events and 1 speeding event. Risk score moves from 2.50 to 7.75. Threshold is 7.00, so the record flips to flagged and appears in the queue. A reviewer confirms or clears it. Payments or appeals adjust the score back down — same mechanism, opposite direction.

3. Domain mapping

The skeleton uses generic entity names. In Big Brother they mean:

Code nameBig Brother meaning
UserReviewer account (admin / senior reviewer / reviewer) and, where reused, the anonymized driver identity. Roles map to review permissions, not surveillance powers.
ProductDriver flag record — one row per anonymized driver. Read sku as driver ID, price as risk score, quantityInStock as pending event count, category as event/violation class.
updateStockAdd an event (+) or resolve one (−). Negative-balance guard prevents resolving more than exists.
low-stockFlag queue query — drivers at or over the threshold.
discontinueClose a flag (cleared / resolved), soft-close that keeps history.
Naming is final: DriverFlag with driverId / riskScore / eventCount / flagThreshold / eventType. If you see old shop words in comments, read “product” as “driver flag record”.

4. File-by-file reference

Paths relative to src/main/java/com/javaproject/. All files are skeletons — signatures and TODOs exist, bodies return stubs.

model/ — Flag and account entities
model/BaseEntity.java
Abstract base class for every record

Common audit fields: id, createdAt, updatedAt, version (optimistic locking), plus equals/hashCode by id and toString. Gives every flag record a stable identity and change history without any location data.

model/User.java (+ UserRole enum, same file)
Reviewer account → users table

Fields: username, email, passwordHash, firstName, lastName, phoneNumber, active, role, lastLoginAt. getFullName(); toString() excludes the hash. Roles ADMIN / MANAGER / USER map to admin / senior reviewer / reviewer.

model/Product.java
Driver flag record → products table (read: driver flags)

Fields: name, description, sku (unique), price, quantityInStock, reorderLevel, category, active, discontinuedAt. Helpers: isLowStock() (count at/over limit → flagged), isAvailable() (active record). Traffic reading: driver ID, risk score, event count, threshold, event class.

config/ — Connection settings
config/DatabaseConfig.java
Jackson-mapped POJO for DB settings

Holds host, port, database, username, password, useSSL, serverTimezone, allowPublicKeyRetrieval, connectionTimeout, maxPoolSize. buildJdbcUrl() composes the JDBC URL; validate() rejects missing host/database/username or bad port.

util/ — Cross-cutting helpers
util/DatabaseConnection.java
Connection manager (single-connection; HikariCP suggested later)

Loads com.mysql.cj.jdbc.Driver once, opens connections via DriverManager with autoCommit=false. testConnection(), close(), initializeSchema() (CREATE TABLE IF NOT EXISTS for users + flag records, plus indexes). No location handling anywhere.

util/ConfigLoader.java (+ ConfigException, same file)
Static JSON config reader/writer

loadDatabaseConfig() (default path then classpath), loadDatabaseConfig(path), saveDatabaseConfig(config, path), createDefaultConfig(path). Failures surface as ConfigException.

util/PasswordUtil.java
BCrypt wrapper for reviewer passwords

hashPassword / verifyPassword / needsRehash / generateSalt / rehashPassword, LOG_ROUNDS = 12. Driver identities are never passwords; only reviewer logins are hashed.

util/PriceUtil.java
Exact decimal math — used for risk scores

SCALE = 2, HALF_EVEN. Static round/add/subtract/multiply/divide/isPositive. Every score update re-rounds so thresholds compare deterministically.

dao/ — Persistence; SQL lives only here
dao/GenericDAO.java
Generic CRUD contract

save / update / deleteById / findById / findAll / existsById / count. Fully defined. Lets the flagging pipeline treat any record type uniformly.

dao/DAOException.java
Checked DAO-layer exception

Carries operation and entityName, enriched getMessage(), factory for duplicate-key / foreign-key SQL errors.

dao/UserDAO.java
Reviewer-account queries (interface, fully defined)

findByUsername, findByEmail, existsByUsername, existsByEmail, findByRole, findActiveUsers, updateLastLogin, searchByName, changePassword. Used by login and account admin — not by driver lookup.

dao/UserDAOImpl.java
JDBC implementation (stubbed)

TODOs specify exact SQL (INSERT with RETURN_GENERATED_KEYS, version-checked UPDATE, case-insensitive LOWER() lookups) plus a private mapResultSetToUser() helper.

dao/ProductDAO.java
Flag-record queries (interface, fully defined — read as DriverFlagDAO)

findBySku (= by driver ID), existsBySku, findByCategory (= by event class), findActiveProducts, findLowStockProducts (= flag queue), searchByName, findByPriceRange (= by score range), updateStock (= add/resolve event), getStockQuantity, discontinueProduct (= close flag). In Big Brother these are called by the automatic scorer, not by a human search box.

dao/ProductDAOImpl.java
JDBC implementation (stubbed)

Same pattern plus flag-specific guards: no negative event counts in updateStock, version-checked writes, soft-close in discontinueProduct, mapResultSetToProduct() helper.

service/ — Rules and scoring; validation lives here
service/ServiceException.java
Checked service-layer exception

Wraps DAOException with a pipeline-level message (optional errorCode).

service/UserService.java
Reviewer-account operations (interface)

registerUser, authenticate, updateProfile, changePassword, findById, findByUsername, getActiveUsers, getUsersByRole, searchUsers, deactivateUser, activateUser, changeUserRole.

service/UserServiceImpl.java
Implementation (stubbed) — validation + hashing

Username/email/password regex checks, uniqueness via DAO, BCrypt hashing, last-login stamping on authenticate.

service/ProductService.java
Flagging operations (interface — read as DriverFlagService)

createProduct (= open flag record), updateProduct, adjustStock (= add/resolve event), findById, findBySku, getActiveProducts, getProductsByCategory, getLowStockProducts (= flag queue), searchProducts, getProductsByPriceRange (= by score), discontinueProduct, reactivateProduct, getStockQuantity, getAllCategories.

service/ProductServiceImpl.java
Implementation (stubbed) — the automatic scorer

Validates driver ID, score, counts; rejects duplicates; rounds scores via PriceUtil; delegates event adds to the DAO; surfaces over-threshold state as the flag. This is where “it finds unsafe drivers” happens — a rule, not a person browsing.

5. Database — and why it can't track locations

Neither table has a location, GPS, route, or address column. The schema only stores identities, counts, scores, categories, and timestamps.

users — reviewer accounts
